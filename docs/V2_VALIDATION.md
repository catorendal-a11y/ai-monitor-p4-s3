# AI Monitor v2 foundation validation

Product direction: **Physical AI Agent Companion & Monitor**. Provider quota/activity,
live agent interaction, companion rendering, transport and hardware capability remain separate domains.
The existing USB/AIM1 snapshot is not a permission or generic live-agent container.

## Analysis fixes

The v1.18.5 analysis identified Windows process cleanup, stalled local readers, brightness recovery,
physical touch cancellation and loop-task soak validation. The source now contains Windows Job Object
containment with synthetic real-process tests, coalesced desktop reads, explicit stalled-reader recovery
messages, and initial brightness recovery which preserves subsequent user overrides.
A permanently blocked reader still requires restarting its owning host/app; this limitation is explicit.
Physical touch fault injection, 24-hour loop-task soak and installation on a fresh PC remain pending.
Native tests do not establish those physical results.

## Added diagnostics

`get_hardware` is a bounded, read-only USB command. It reports actual physical flash/PSRAM size,
running image and application partition size, internal/external heap totals/free/minimum/largest block,
chip revision, configured CPU/flash frequency, SDK version and display buffer allocation.
Free application space is `partitionBytes - applicationBytes`, not free flash over the whole chip.
External allocator capacity is separate from physical PSRAM (particularly relevant to S3 PSRAM XIP).

Compiled ESP-Hosted/PPA capability is distinguished from runtime detection. C6 is explicitly
`not-probed`, its version is unknown, and production PPA acceleration is inactive. SD detection is pending.
Four one-time `startupMemory` readings now cover before display, after display, after LVGL, and
after companion screen creation. They include internal/external total/free/minimum/largest blocks
and uptime. Missing stages are explicitly uncaptured. The final stage includes all initial screen
creation, not only companion assets; it precedes steady-state rendering. Allocations by concurrently
started USB tasks can also affect that final reading.
The owner's reported PCB is **JC4880P443C_I_W_Y**; wiring and actual SD presence still need verification.
No active coprocessor initialization or C6 firmware update is performed by these commands.

Stop the host attached to the selected device before using the development collectors:

```text
python scripts/collect_device_baseline.py --board guition-p4 --port COM_NUMBER --output work/hardware.json
python scripts/collect_graphics_baseline.py --board guition-p4 --port COM_NUMBER --seconds 10 --output work/graphics.json
```

Replace `COM_NUMBER` with the explicitly identified device port. Port auto-selection is rejected.
The collectors validate firmware identity and output only whitelisted diagnostic fields.
These commands are developer tools. The desktop Host settings page now has Device diagnostics:
the existing host requests one validated snapshot after a capability-aware connection handshake.
It never opens a second COM connection or treats the snapshot as continuous memory telemetry.
Firmware must advertise `hardwareDiagnostics: true`; older firmware keeps normal USB monitoring
without an unsupported diagnostic request. Invalid/unsolicited replies and mismatched boot identities
cannot populate the diagnostic display. Lost connection/status clears the visible sample.

## Graphics benchmark environments

- `esp32p4-graphics`: CPU rotation and driver submission counters.
- `esp32s3-waveshare-43-graphics`: copy/submission counters.
- `esp32p4-ppa-benchmark`: one isolated CPU-versus-PPA scratch-buffer rotation test during startup.

Production environments keep timing instrumentation off. `get_graphics` returns counters and
`get_ppa_benchmark` reads the isolated test result; neither command starts a test, changes settings,
enables acceleration or renews the provider host lease. Flush chunks are not physical display FPS.
The PPA test uses separate aligned PSRAM scratch buffers and checks every output byte. On a timeout
it retains DMA-owned resources until reboot rather than freeing memory still potentially in use.
These benchmark environments have compiled, but physical timing and orientation validation are pending.

## Companion assets

All twelve NOVA/ORBIT poses use one union-alpha crop per companion. Raw RGB565+A8 data decreased
from **4,396,320 to 3,349,656 bytes**, saving **1,046,664 bytes (23.8%)**. Frame origins preserve
placement between poses. Built-in frames remain the production fallback.

The trusted export verifies all generated bytes against the committed C++ images:

```text
node scripts/export_companion_frames.cjs --output work/asset-benchmark-input
python scripts/benchmark_asset_codecs.py --frames work/asset-benchmark-input --output work/asset-codecs.json --cc gcc
```

The export needs Node and Sharp; the benchmark needs the pinned LVGL source and a C compiler.
Preliminary host-only payload sizes for all twelve frames:

| Format | Bytes |
| --- | ---: |
| Raw | 3,349,656 |
| RLE | 1,925,271 |
| LZ4 | 519,579 |
| Deflate | 249,490 |

These are exact encoded payload sizes, not ESP32 decode timings. The benchmark also counts a
prototype delivery manifest. Its multi-companion benchmark metadata is not the runtime pack schema.
No runtime codec choice has been finalized or production decoder enabled.

The version-1 single-companion manifest and two-slot caller-supplied cache have synthetic native
tests. They reject invalid sizes, hashes, traversal, duplicate fields, invalid UTF-8, case aliases
and reserved device filenames. Failed decoding/hash verification cannot overwrite a pinned active
frame. The cache is not yet connected to a PSRAM allocator, actual hash/decode implementations,
LVGL lifetime management or SD. Those integrations require their own tests before enabling packs.

## Verification and remaining gates

The foundation passed 306 Python regressions, strict C++ protocol/settings/live-agent tests and both board
identities, real native LVGL UI tests for P4/S3, and production firmware builds for both boards.
P4 production build: application **4,570,004 / 6,553,600 bytes**, static RAM **100,068 / 327,680 bytes**.
Static linker RAM usage is not runtime heap or total physical SRAM consumption.

The P4 production candidate was subsequently flashed and verified byte-for-byte. Partition layout
matched before application-only writing; NVS was not written. The previous application was backed
up locally outside the public repository. A normal post-flash reset did not start the app on this
device; watchdog reset did. The P4 flasher now explicitly requests that reset. S3 retains UART hard reset.

Physical USB telemetry confirmed v1.19.0, 16,777,216 bytes flash, 33,554,432 bytes PSRAM and
**4,604,272 bytes serialized application / 1,949,328 bytes free application partition space**.
Serialized image size differs from linker flash usage above. At the recorded connection snapshot,
PSRAM free/largest were **29,710,160 / 29,360,116 bytes**; internal heap free/largest were
**228,120 / 102,388 bytes**. These are measurements at one point, not long-term minima or guarantees.

| Startup checkpoint | Internal free | Internal largest | PSRAM free | PSRAM largest |

Runtime heap can increase when the startup/Arduino loop task releases its stack. Native touch tests
passed, but physical gestures/fault injection and 24-hour soak remain pending. No runtime C6 test,
BLE pairing, Claude Desktop exchange, permission approval, SD activation or installer release is claimed.
Follow [the construction plan](../plans/COMPANION_V2.md) for incremental implementation and physical gates.
The separate [Claude live foundation](CLAUDE_LIVE_FOUNDATION.md) now has a tested bounded parser
and permission state machine; it is not connected to the UI or a transport yet.

### Follow-up source validation

The desktop flasher now checks the selected board's identity after writing and rebooting before
reporting verified startup. USB re-enumeration retries are bounded and never select another port
or repeat a write. An unconfirmed boot explicitly reports that writing finished and directs the
user to reconnect USB and check the connection; it does not advise erasing device settings.

The follow-up source passed 306 of 312 Python tests. The six errors occurred when Windows denied
the per-user local IPC server inside the restricted execution environment; those tests remain
unverified here. The 36 desktop action/UI tests and nine board/flasher tests passed. Strict native
protocol tests and real LVGL UI regressions for both board identities passed.

The current cross-build could not run the ESP32 toolchain in this execution environment
(Windows reported Illegal System DLL Relocation). GitHub DNS access was also unavailable.
These environmental failures are not a successful firmware build, release, or physical test of
the follow-up changes. The hardware-diagnostics advertisement and post-flash boot verification
still require a fresh firmware build and physical installation test before publication.
